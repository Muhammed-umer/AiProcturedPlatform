Camera Proctoring & AI Question Generation

Two additions to the department's exam platform: a live-webcam proctoring layer during tests, and a subject-driven AI question generator for staff — both built to keep working on the offline lab LAN.

Scope · 2 features, 1 sequenced build Stack · Next.js 16 · Drizzle · PostgreSQL Status · ready to implement

01 — At a glance

What we're adding

Both features reuse machinery the app already has, so the new surface area is small and the risk stays contained.

Feature B · during the exam

Live camera proctoring

Each student's webcam is required and stays on. The app takes periodic snapshots and runs on-device face detection to flag no face, multiple faces, and camera off — flags that escalate through the existing warning system. Runs fully offline on each lab PC.

Feature A · while preparing a test

AI question generation

Staff pick Subject → Subtopic → Difficulty → Type → Count (with an optional free-text topic) and Claude drafts the questions. Everything lands on the existing review screen — nothing saves until a human approves it.

02 — The one hard constraint

🔒

Cameras need HTTPS

Browsers only allow webcam access in a secure context — HTTPS or localhost. The app currently runs over plain HTTP (http://<server-ip>:3000), where a lab desktop's camera silently fails. So proctoring forces a one-time move to HTTPS on the lab server (a reverse proxy with a certificate trusted on the ~60 machines). Development on localhost is unaffected.

03 — Decisions locked

Choices you made

Camera flags
count toward warnings They escalate like tab-switching and can auto-submit. A sustained-duration debounce is added so a glance down never ends a test.
Snapshot retention
latest + flagged only One live thumbnail per student plus a frame at each violation — small enough to live in Postgres, so pg_dump backs it up. No separate file store.
Topic input
dropdowns + free-text Seeded, admin-editable Subject/Subtopic lists, plus a free-text override for anything not listed.
Build order
both, one plan Sequenced so the generator (no deployment change) is usable before the proctoring work lands.

04 — Feature A · detail

AI question generation

Slots into the existing extract → review → commit pipeline. The generator only changes the input — from "a document" to "a taxonomy selection."

A1

Taxonomy in the database

New admin-editable subjects and subtopics tables, seeded with a starter set (Computer Networks, OS, DBMS, OOPS, DSA, Java, Python, C, Aptitude, Logical Reasoning, Verbal). A small admin page manages them.

schema.tsscripts/seed.ts+ admin/subjects/page.tsx+ actions/taxonomy.ts
A2

Generation library

A new ai-generate.ts mirrors the proven ai-parse.ts: same Claude client, claude-opus-5, the strict tool schema, and the refusal guard. The model is told to produce exactly N questions at the chosen difficulty, give each an explanation, and self-verify the marked answer.

+ lib/ai-generate.tslib/ai-parse.ts
A3

Shared review screen & panel

The existing ReviewScreen is extracted so both document-import and generation use the same reviewer. A new cascading dropdown panel drives generation and feeds drafts straight into it; saving reuses commitReviewedQuestions unchanged.

+ question-generate.tsx+ review-screen.tsxtests/[id]/page.tsx+ actions/generate-questions.ts

05 — Feature B · detail

Camera proctoring

Capture and detection run on each student's PC; flags travel through the same funnel as every other violation, and the server stays authoritative.

B1

HTTPS & cookie

Serve the app behind a Caddy reverse proxy with a locally-trusted certificate; make the session cookie's secure flag environment-driven. Documented in the README's lab-server section.

lib/session.ts.env.exampleREADME.md
B2

Snapshot storage

A new proctorSnapshots table holds the latest thumbnail (one upserted row per student) plus flagged frames, stored as compact base64 JPEGs directly in Postgres.

schema.ts
B3

Capture, gate & detection

A camera gate on the start button (alongside the fullscreen gate) requires webcam permission. Bundled MediaPipe face detection runs on a throttled loop; a small pure, unit-tested state machine debounces the flags before they fire through the existing flag() funnel.

+ proctor-camera.tsx+ lib/proctor-flags.ts+ actions/proctor.ts+ public/proctor/*exam-runner.tsx
B4

Live monitor integration

An image route streams each student's latest frame so the 5-second poll stays light; the monitor cards gain a webcam thumbnail and the new flag types get human labels.

+ api/proctor/[attemptId]/latestactions/monitor.tsmonitor-view.tsx

07 — How we'll prove it works

Verification

  • ›Unit tests — the flag debounce state machine (a glance never flags, sustained absence flags once, recovery resets) and the generation draft-mapping, as pure logic.
  • ›End-to-end — drive generation to a saved question with a deterministic stub; drive the camera gate with a fake media device and assert a snapshot appears on the monitor.
  • ›Manual pass — over localhost: cover the camera → a flag appears after the debounce, the warning increments, and the thumbnail shows on the monitor; then generate Java → Collections → Medium → 5 MCQs → review → save.
  • ›Cost — generation is authoring-time only: roughly $3–4 per 1,000 questions on claude-opus-5. Negligible in practice.

08 — Open risks

What to watch

HTTPS trust rollout

The certificate must be trusted on all ~60 lab machines before a real drive — otherwise the camera fails everywhere. This is the biggest operational dependency.

Face-detection false positives

Mitigated by the debounce. If invigilators still see noise, the thresholds are the tuning knob — or we revisit the alert-only policy.

AI answer correctness

Mitigated by mandatory human review, model self-verification, and confidence flagging. Nothing saves without an admin approving it.
